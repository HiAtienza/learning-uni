# Join, Aggregation and Set Evaluation

## In 60 Seconds

The smaller relation is not always the cheapest outer input, and the fewest transferred blocks do not always yield the shortest time. In Lecture5b's example, indexed nested loops uses 25,100 transfers but also 25,100 seeks; block nested loops uses 40,100 transfers and only 200 seeks. At 0.1 ms per transfer and 4 ms per seek, the estimated times are 102,910 ms and 4,810 ms. This local arithmetic explains the source's comparison without claiming a database benchmark.

## Define the Result Before Choosing the Algorithm

A natural join matches all shared attribute names and returns one copy of those shared columns. It is not a Cartesian product without conditions, nor a join on a guessed single attribute when several names are shared. The physical strategy must preserve the same result. Source: Lecture5b pp.3–4.

The lecture uses customer:10,000 records/400 blocks and depositor:5,000 records/100 blocks. Lab4 instead uses much larger relations. Do not carry the lecture's cardinalities into the tutorial. Default lecture estimates are pessimistic unless memory availability says otherwise. Source: Lecture5b pp.5–8; Lab4 p.2.

## Compare Tuple and Block Nested Loops

For outer r, inner s, and little memory, tuple nested loops transfers $B=b_r+n_r b_s$ with $S=b_r+n_r$ seeks. Each outer tuple triggers another inner scan. The two source orientations give depositor outer:2,000,100 transfers/5,100 seeks; customer outer:1,000,400/10,400. Their time ordering depends on the transfer/seek weights.

Block nested loops reuses each outer block for every tuple pair with an inner block. The source's one-outer-block model costs $B=b_r+b_r b_s$, $S=2b_r$. Depositor outer costs40,100/200; customer outer40,400/800. These are the source model, not a formula for an arbitrary multi-block outer buffer. If the smaller relation fits completely as the retained inner input, the source simplifies to $b_r+b_s$ transfers and2 seeks. Source: Lecture5b pp.6–10.

## Probe the Inner Index Without Hiding Retrieval Cost

Indexed nested loops applies to equality/natural joins when the inner join attribute has a suitable index. For each outer tuple, probe the index and fetch all matching inner records. With one matching key record and h index accesses, $B=b_r+n_r(h+1)$ and the deck uses the same count for seeks. In its depositor/customer example, h=4 yields25,100/25,100.

For a non-key clustered lookup, transfer and seek costs differ: per probe, h+b transfers but h+1 seeks, where b is matching data blocks. Estimate b from supplied statistics or state the assumption; “one lookup” does not mean “one block”. Real caching and repeated keys can reduce actual work; do not silently add that benefit to the cold source model. Source: Lecture5b pp.11–13; Lecture5a pp.7–10.

## Merge Sorted Inputs and Account for Sorting

Sort both inputs on the join attributes if necessary, then advance pointers, retaining matching equal-key groups. The stated merge scan costs $b_r+b_s$ transfers and $\lceil b_r/b_b\rceil+\lceil b_s/b_b\rceil$ seeks, assuming each equal-key group fits in memory. Duplicate keys require producing every matching pair. The source's one-pass scan estimate can fail when groups do not fit.

Keep output conventions explicit: materialising sorted files adds their final writes before a later join reads them. If final merges stream directly into the join, do not charge an additional full input scan for the same reads. Buffer feasibility still has to hold for both inputs. Source: Lecture5b pp.14–16; Lecture5a p.21. The accounting clarification prevents incompatible formulas being combined.

## Partition With One Hash and Probe With Another

Partition both relations using the same hash of join attributes so equal keys land in corresponding partitions. Keep the smaller build partition in memory, build a hash table using a different hash function, then scan the corresponding probe partition and emit all actual key matches. A hash collision alone is not equality. Cross-partition comparisons are unnecessary; the probe partition need not fit entirely in memory. The source handles equality/natural joins, not arbitrary inequalities. Source: Lecture5b pp.17–20.

Choose enough partitions for build partitions to fit; allow room for skew, buffers and the in-memory table. A fudge factor is a planning allowance, not a proof that every partition fits. A one-pass partition stage with n_h output buffers of b_b blocks plus an input buffer of b_b blocks requires at least $(n_h+1)b_b$ frames. This direct buffer count is needed when using the tutorial's assumptions.

## Read the Hash-Join Cost as a Conditional Model

The supplied estimate is $B=3(b_r+b_s)+4n_h$ and $S=2(\lceil b_r/b_b\rceil+\lceil b_s/b_b\rceil)+2n_h$. The correction budgets writing and rereading partially filled partition blocks. For b_r=400,b_s=100,n_h=5,b_b=3, B=1,520 and S=346. The simple three-times base counts partition-read, partition-write and join-read; output-result writing is omitted. If the whole build fits and partitioning is unnecessary, the deck gives one scan of both inputs and2 seeks. Source: Lecture5b pp.21–22.

The lecture's example assigns a20-block build partition to20 memory blocks; an implementation also needs buffers and hash-table overhead. Treat its arithmetic as an idealised cost model, not proof that all allocations fit simultaneously. Skew or recursive partitioning changes the cost.

## Aggregate and Implement Set Operations

Sorting or hashing groups equal keys for COUNT,MIN,MAX,SUM and AVG. Partial AVG must retain both sum and count: an unweighted average of group averages is generally wrong. For set union, keep distinct tuples from either side; for intersection, keep tuples present in both; for r−s, remove s tuples from the r set. Corresponding hash partitions must use a compatible first hash and then check actual tuple equality. Preserve the distinction between set semantics and SQL bag variants such as UNION ALL. Source: Lecture5b pp.23–24; SQL distinction retained from Unit 05.

## Return to the Weighted Comparison

The opening indexed join costs $25100(0.1+4)=102910$ ms. Block nested loops costs $40100(0.1)+200(4)=4810$ ms. Hash join costs $1520(0.1)+346(4)=1536$ ms under the source's idealised assumptions. These are conditional estimates; include sorting, partition overflows, output policy and actual statistics before choosing a plan. The required question is “cheapest under which model?”, not “which algorithm is always best?”.

> [!success]- Answer

> [!success]- Answer

> [!success]- Answer

>
> Source: Lecture5b pp.19–20.

> [!success]- Answer
> Equal keys hash together, but different keys can collide; check actual equality before emitting.
>

### Card 07 — What state supports correct partial AVG?

> [!success]- Answer
> Sum and count; combine their sums, then divide total sum by total count.
>
> Source: Lecture5b p.23.
