# Software Processes

[[10_UNIVERSITY_CS/Software Engineering 1/Tutor Mode/00 Start Here|Tutor start]] · [[10_UNIVERSITY_CS/Software Engineering 1/Tutor Mode/Unit 02 - Software Processes/01 Tutor Notes|Tutor notes]] · [[10_UNIVERSITY_CS/Software Engineering 1/Tutor Mode/Unit 02 - Software Processes/02 Recall and Exam Practice|Recall and practice]] · [[10_UNIVERSITY_CS/Software Engineering 1/Unit 02 - Software Processes/01 Notes|Standard reference]]

## In 60 Seconds

A process model is a simplified picture of how development work is organized. This unit teaches three mechanisms: Waterfall makes phase outputs and agreements explicit; incremental development creates opportunities to learn from working versions; reuse-oriented development reconciles needs with available software. All three still require specification, design/implementation, validation and evolution.

You should be able to choose a process basis from project conditions, explain its benefit and limitation, trace a change through dependent work, and distinguish planning tests from running them. The important question is not which model is universally best, but which mechanism addresses the uncertainty and consequences in front of you. Source: S17 PDF pp.3–13,15–49,52–67.

## Concept Preview

> [!info] Process versus model
> **Concept:** Process versus model.
>
> **Plain-language meaning:** Real teams do activities; a model abstracts how those activities are organized.
>
> **Why it matters:** A model name cannot prove the team performed the necessary work.
>
> **Connects to:** roles, artifacts and evidence.
>
> **Source:** `Week2-Lecture-Software Processes-r.pdf`, PDF pp.3–4,10–13.

> [!info] Phase commitments
> **Concept:** Phase commitments.
>
> **Plain-language meaning:** Waterfall uses distinct stages and reviewed outputs to coordinate work.
>
> **Why it matters:** Changing an agreed input can require changes and approval in downstream work.
>
> **Connects to:** requirements stability and change cost.
>
> **Source:** `Week2-Lecture-Software Processes-r.pdf`, PDF pp.15–21.

> [!info] Useful increments
> **Concept:** Useful increments.
>
> **Plain-language meaning:** Build a useful part, check it with the existing system and learn before choosing more work.
>
> **Why it matters:** Early feedback can correct assumptions before every feature is built.
>
> **Connects to:** uncertainty, dependencies and integration.
>
> **Source:** `Week2-Lecture-Software Processes-r.pdf`, PDF pp.28–37.

> [!info] Fit through reuse
> **Concept:** Fit through reuse.
>
> **Plain-language meaning:** Understand needs, examine candidate capabilities, then negotiate fit before integration.
>
> **Why it matters:** Less new code does not automatically mean the right system.
>
> **Connects to:** two requirements activities and supplier control.
>
> **Source:** `Week2-Lecture-Software Processes-r.pdf`, PDF pp.46–49.

## 1. What does a process model leave out?

**Intuition.** A route map can show major stops without specifying who drives, whether the vehicle works, or how a disruption is handled. A process model similarly simplifies real work. Its usefulness is coordination and reasoning, not a guarantee of execution quality.

A **software process** is the actual related activities, methods and practices used to develop and maintain software. A **process model** represents selected activities and their organization. A real process must supply local roles, outputs, reviews, tools and constraints. The source's broad claim that a model “ensures” good practice should be understood as its intended support, not proof of an outcome. [^model]

**Worked inference.** “We follow Waterfall” tells you something about intended phase organization. It does not tell you whether the requirements were correct or the test results were inspected. Ask what artifact was produced, who reviewed it and what evidence supports the claim. The same challenge applies to “we are agile.”

The lecture names other model families for orientation, but fully develops the three below. Naming a Spiral or V-Model here is not a substitute for source-supported instruction in that method.

## 2. When are phase outputs useful—and expensive to change?

**Problem first.** If design was approved using a requirement that later changes, why does the correction cost more than editing one sentence?

Waterfall represents principal work as stages: requirements analysis/definition; system/software design; implementation and unit testing; integration and system testing; operation and maintenance. Each stage produces an output that informs later work. A **deliverable** is an output to supply; a **milestone** is a significant point in the plan. The phase structure makes commitments and progress artifacts visible. [^waterfall]

![[10_UNIVERSITY_CS/Software Engineering 1/Unit 02 - Software Processes/Attachments/waterfall-phases.svg]]

**Figure 1 — Read the outputs between stages**

**Read it:** Follow the main progression downward. Implementation already includes unit testing. The source allows overlap and feedback; this simplified sequence does not prohibit rework.

**Key takeaway:** A downstream stage relies on decisions made earlier, which is why changing them has consequences.

**Provenance:** Unchanged standard teaching SVG based on S17 PDF pp.15–21; informal process diagram.

**Visible worked trace:** A requirement says a report covers one term. After design approval it changes to compare several terms. First identify affected design/data decisions. Then identify code and expected test results based on the old scope. Update those artifacts and repeat appropriate reviews. The propagated work plus reapproval—not merely the size of the edited requirement—explains the schedule and budget cost in Lab Q4. Reducing avoidable revisits is sensible; preserving a known serious mistake to protect a schedule is not the implication. [^waterfall]

**When it helps.** Stable, understood requirements and explicit review obligations can make phase agreements valuable. Documentation preserves reasoning and supports planning. **Limit:** document approval cannot reveal every problem users would notice in the working whole. If assumptions are highly uncertain, late feedback can invalidate much completed work. [^tradeoffs]

> [!warning] Source reconciliation: testing and risk
> **SOURCE A:** S17 p.25 says testing is late and risk management is not inherent. **SOURCE B:** pp.16–17 include unit testing; pp.62–63 include reviews and early test plans; p.24 praises controlled change. **CONFLICT:** an absolute reading makes these incompatible. **SAFEST INTERPRETATION:** whole-system execution may arrive late, but early reviews, unit checks and planning remain possible; change control supports risk work without replacing explicit risk analysis. **CONFIRMATION STATUS:** interpretation, not an instructor-confirmed correction. Exact assessment wording remains unconfirmed.

## 3. What does an increment let the team learn?

**Problem first.** An online flower shop cannot yet take payment. Can showing its listing and registration functions still be useful?

An **increment** adds functionality to a previous version. Incremental development interleaves specification, development and validation: evidence from building or checking one part can change what is specified next. Interleaving is about information flowing during the work, not an excuse for undefined requirements. [^increments]

**Work through the source case:** begin with an outline of the shop's needs; select listing and registration; specify, design and build those functions; unit-test and integrate them; expose the version to users; use feedback to plan cart/checkout, followed by later payment, tracking and reviews. Listing alone cannot deliver the final purchase workflow, but it can expose misunderstandings about navigation and product presentation earlier. Be explicit about that partial value. [^increments]

**Why it helps.** The team commits less work before seeing selected user evidence. Feedback can redirect later effort. A useful early release may deliver value while the rest is built. These benefits require actual feedback and a meaningful decomposition.

**Dependency counterexample.** Suppose feedback changes the meaning of a product variant. The current cart and an earlier listing may both depend on it. S17 p.32's claim that only the current increment changes is therefore a favorable local-change case; pp.36–37 explicitly warn about dependencies across increments. Earlier work may need revision and regression checks. Supporting an old increment while building a new one also consumes resources.

Incremental delivery is not identical to agile. A team can plan increments in detail long in advance. The source's agile introduction adds an emphasis on adaptation, customer collaboration and short feedback cycles; Scrum is taught next. [^increments]

> [!question] Explain it yourself
> Why can three numbered releases still fail to provide the learning benefit of incremental development?

> [!success]- Check your explanation
> If no useful feedback influences later decisions, the releases may merely divide delivery dates. Dependencies, integration and validation still need management. Source: S17 PDF pp.29,32–37,74.

## 4. Why does reuse require requirements work twice?

**Problem first.** A replacement package is attractive, but cannot perform one essential university workflow. Should the team simply remove that requirement?

**Intuition.** Shopping for a ready-made part requires knowing both what you need and what is actually available. Reuse-oriented engineering makes that reconciliation explicit. It can use web services, packaged components or configured stand-alone systems; framework names in the lecture are examples, not selected course tools. [^reuse]

![[10_UNIVERSITY_CS/Software Engineering 1/Unit 02 - Software Processes/Attachments/reuse-and-requirements.svg]]

**Figure 2 — The information changes between requirements activities**

**Read it:** Requirements specification → component analysis → requirements modification → system design with reuse → development/integration → system validation.

**Key takeaway:** You learn candidate capabilities after setting broad needs, so the second requirements activity has different information.

**Provenance:** Unchanged standard teaching SVG, checked against S17 PDF p.47; informal flow, not UML.

**Worked negotiation:** state the required accounting services and integration constraints first. Evaluate candidate packages against those needs. Then separate acceptable adaptations from essential gaps: negotiate a changed workflow when it preserves the real need; plan additions when feasible; reject a candidate when an essential need cannot reasonably be met. Design and integrate the chosen combination, then validate the whole. This is the source's two requirements activities made operational. [^reuse]

Reuse can reduce new development, cost and time, but may introduce requirement compromises and dependency on supplier evolution. “Already exists” is evidence of availability, not suitability. A generic supplier's update does not automatically respect the commissioned system's promises.

## 5. Which work remains in every process?

**Question.** If a team chooses a model, can it omit work not drawn in the diagram? No: a simplified representation does not remove the underlying obligations. [^activities]

| Activity | Mechanism and useful output |
|---|---|
| Specification | Check feasibility; elicit/analyze needs; record user/system requirements; validate the agreed document |
| Design and implementation | Define architecture, interfaces, components and data; implement, review, build and integrate |
| Validation | Inspect artifacts and execute suitable checks; compare evidence with requirements and customer needs |
| Evolution | Correct faults, adapt to environments, improve qualities and prevent future problems |

Architecture concerns main components and their relationships. Interfaces specify interactions; ambiguity can make separately correct components fail together. Component design specifies internal operation or changes to a reused part. Data/database design is in this course's source, but no particular DBMS is selected. Supporting work includes planning and risk management, version/change/build control, deployment and training, documentation and process improvement. [^activities]

**Testing is not one undifferentiated event.** Component tests check parts, system tests check the integrated whole, and acceptance tests examine operational suitability with customer data/needs. Test planning specifies what evidence will be needed; execution produces actual observations. Requirements and system specifications can inform an acceptance-test plan before an executable system exists. System specification/design inform integration planning; execution later checks the built product. The p.63 diagram shows these relationships. [^validation]

**Visible worked example:** for a journey planner, component evidence can check a cost calculation for controlled input; system evidence checks that the displayed route matches the selected result; acceptance evidence checks intended users' journey cases. Passing the first does not establish the other two. Regression tests recheck previously tested behavior after changes. Source language about “free of defects” is a goal, not a universal guarantee from sampled executions. [^validation]

## Return to the motivating question

- **Braking controller:** the source favors a plan-driven/Waterfall basis because failure consequences demand careful upfront analysis and evidence. Confirm timing, hardware and assurance needs. The process name alone does not establish safety.
- **Novel research VR:** use increments and possibly UI prototypes to discover needs. Confirm the intended users and evaluation purpose; a prototype is feedback evidence, not proof of final quality.
- **Accounting replacement:** evaluate reuse because established needs and integration with existing systems may fit available software. Confirm actual candidates before treating this as feasible.
- **Journey planner:** use meaningful increments and user feedback to refine interaction needs. Confirm whether partial versions are useful and what environmental-impact assumptions mean.

These reproduce the lab's recommendations while exposing their conditions. A project can combine mechanisms. Criticality and uncertainty are independent dimensions: internal learning may be needed even when deploying incomplete operational behavior is unacceptable. [^lab]

## Guided, independent and transfer practice

### Problem G1 — Trace the cost of a revision

**SUPPLEMENTARY PRACTICE.** Synthetic scenario; principles from `Week 2-Lab- Software Process-Example-Answer.pdf`, PDF p.2 Q4.

After a requirement is approved, its meaning changes. Trace two downstream artifacts that may need revision and explain why repeated revisits can affect the budget.

> [!tip]- Hint
> Follow what consumed the earlier requirement; include review work.

> [!success]- Solution
> A design may encode the old requirement, so its responsibilities or interfaces must be reconsidered. Test expectations may also encode the old behavior and need revision. Code and documentation can be affected too. Updating and reviewing those dependent artifacts consumes effort; repeated reapproval adds cost. Limit avoidable churn, while still correcting necessary defects.

### Problem O1 — L3 — Two requirements activities in reuse

**ORIGINAL COURSE EXERCISE** · **Difficulty:** ★☆☆

**Source:** Week 2-Lab- Software Process-Example-Answer.pdf, PDF p. 2, Q3.

Consider the reuse-based process model. Explain why it is essential to have two separate requirements engineering activities in the process.

> [!tip]- Hint
> What can you know before component analysis, and what do you learn only after it?

> [!success]- Solution
> **Before selection:** understand the needed functions and broad constraints well enough to evaluate candidate systems/components.
> 
> **After selection:** compare actual capabilities with business needs; identify needed changes/additions and negotiate acceptable requirements modifications.
>

Skipping the first activity makes selection directionless; skipping the second risks pretending the selected component meets needs it does not meet. ### Problem D1 — Diagnose the timing argument

**SUPPLEMENTARY PRACTICE.** Synthetic scenario; principles from `Week2-Lecture-Software Processes-r.pdf`, PDF pp.62–63,71.

A manager says acceptance-test planning must wait because system testing follows implementation in the phase sequence. Use the source diagram to evaluate this claim.

> [!success]- Solution

### Problem T1 — Choose mechanisms under mixed conditions

**SUPPLEMENTARY PRACTICE.** Synthetic scenario; principles from `Week2-Lecture-Software Processes-r.pdf`, PDF pp.7,13,19,29,36–37,62–66.

A fictional controller project has serious failure consequences, but its operator display is unfamiliar to users. Operational release must include the complete required behavior. Explain why neither “freeze everything now” nor “deploy each incomplete feature” follows automatically. Propose a justified combination of process mechanisms.

> [!tip]- Hint
> Treat failure consequences, uncertainty and permission to deploy partial behavior as separate conditions.

> [!success]- Solution
> **Need for control:** serious failure consequences support early agreement on critical requirements, interfaces and planned evidence. **Need for learning:** unfamiliar interaction supports prototyping or internal increments to obtain user feedback before committing to every display detail. **Deployment boundary:** internal incremental development does not authorize releasing operationally incomplete behavior. Combine learning cycles with controlled baselines and whole-system validation before the required complete release. This is a proposed process rationale, not an assurance design or safety guarantee.
